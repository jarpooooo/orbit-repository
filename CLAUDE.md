# Orbit Repository (PinjamTEDI)

Facility-borrowing web app ("PinjamTEDI"), built from the Figma file "Orbit repository". All pages exist. Facilities, requests, and accounts live in Firebase (project `pinjamtedi`); availability per day/session is still simulated.

## Stack
- Next.js 16.4 (App Router, Turbopack), React 19.3, TypeScript
- Tailwind CSS v4 (CSS-first `@theme`, no tailwind.config), loaded through `@tailwindcss/turbopack`
- `lucide-react` v1 (icons), `motion` (animation), `lenis` (smooth scroll)
- `next.config.ts` enables `cacheComponents`, `partialPrefetching`, `experimental.agentFeedback`; redirects for the old Indonesian URLs and no-cache headers for `/sw.js` live there too. Runs as a Next server (dynamic rendering).

Next.js 16 differs from older versions. Read `node_modules/next/dist/docs/` before using a Next API.

## Commands
- `npm run dev`: dev server
- `npm run emulators`: Firebase Auth + Firestore emulators (needs JDK 21, found by `scripts/emulators.mjs`; data kept in `emulator-data/`). `NEXT_PUBLIC_USE_EMULATORS=true` in `.env.local` points the app at them.
- `npm run seed` / `npm run seed -- --cloud`: write `FACILITIES` to Firestore `facilities` (emulator / real project; replaces the documents)
- `firebase deploy --only firestore:rules`: publish `firestore.rules`
- `npm run build`: production build
- `npm run deploy:firebase` (`-- preview` for a 7-day URL): deploys to https://pinjamtedi.web.app (Firebase Hosting, free Spark plan). The repo stays dynamic; `scripts/deploy-firebase.mjs` temporarily switches the files it lists to a static export (client-side catalog filters, metadata routes as files in `public/`, OG image from `scripts/firebase-static/`, redirects + headers in a `hosting` block), builds against the real project, deploys, then restores every file. If you change `next.config.ts` redirects/headers, `app/manifest.ts`, `robots.ts`, or `sitemap.ts`, mirror it in that script. The dynamic version (Next server) needs App Hosting (Blaze) or Vercel.
- `npm run lint`: ESLint (flat config, `eslint-config-next`)

There is no test setup.

## Layout
- Routes are English: `catalog`, `catalog/[slug]/{schedule,request,letter,summary}`, `room-schedule`, `room-schedule/most-borrowed`, `my-requests`, `how-to-borrow`. `next.config.ts` permanently redirects the old Indonesian URLs (`/katalog`, `/jadwal-ruang`, ...). URL query params are still Indonesian (`q`, `kategori`, `hari`, `mulai`, `selesai`, `ambil`, `kembali`, `jumlah`, `kode`).
- `app/layout.tsx`: root layout (Navbar + Footer, site metadata). `app/page.tsx` and `app/home/page.tsx` both render `components/home/home-content.tsx`.
- `app/components/`: `home/` (home sections), `catalog/` (catalog + request flow), `layout/` (navbar, footer, breadcrumb, stepper, ...), `ui/` (small shared pieces such as `status-badge.tsx`).
- `app/data/facilities.ts`: language-neutral facility data and domain types (`FacilityCategory`, `CATEGORY_ORDER`, `PermissionLevel`, `AvailabilityStatus`, `STATUS_STYLES`, `SUBCATEGORIES`, ...), plus `getFacility`, `getFacilitiesByCategory`, `CATEGORY_COUNTS`, `countInGroup`. See "Facilities" below. `app/data/site.ts`: SEO/site info.
- `app/i18n/`: UI text dictionaries (Indonesian / English), see "Language" below.
- `app/lib/`: `date.ts` (date helpers + Indonesian day/month names), `booking.ts` (room hours `OPEN_HOUR`–`CLOSE_HOUR`, booking rules, query parsing), `nim.ts` (`NIM_PATTERN` `24/541234/SV/25123`, same regex in `firestore.rules`), `permission-letter.ts` (fills `public/templates/permission-letter.docx`).
- SEO: root `metadata` in `app/layout.tsx`, `app/opengraph-image.tsx` (link preview, prerendered; art + Lilita One loaded in `"use cache"` helpers), `sitemap.ts` (public pages + facility details only), `robots.ts`, `not-found.tsx` (translated 404). Signed-in pages and booking steps are `noindex`. `SITE_URL` = `NEXT_PUBLIC_SITE_URL`, else https://pinjamtedi.web.app in production builds.
- PWA: `app/manifest.ts` (install, icons in `public/icons/` rendered from `logo.svg`, shortcuts), `public/sw.js` (network-only; serves `public/offline.html` when a page cannot load; bump `VERSION` when either file changes), `components/layout/service-worker.tsx` (registers it when idle, production only; unregisters in dev), `/sw.js` no-cache headers in `next.config.ts`, `appleWebApp` + apple-touch-icon in `app/layout.tsx`. Install = the browser own prompt/menu (no custom button). `offline.html` is self-contained (inline CSS with the THEME token values, ID/EN + dark from localStorage); keep it in sync if the tokens change.
- `app/globals.css`: imports Tailwind, `colors.css`, `typography.css`. Use `font-display` / `font-sans` utilities for fonts.
- `app/design/`: design system
  - `colors.css`: tokens. (1) PALETTE: `navy`, `royal`, `periwinkle`, `grape`, `mint`, `sun`, `tangerine`, `slate`, each 50–950, plus single Figma colors; steps marked `= Figma` match the design exactly. Same in both themes. (2) THEME tokens (`@theme static`), each written once as `light-dark(<light>, <dark>)`. (3) SEMANTIC tokens in `@theme inline` (brand, on-*, status, level, category, rank). (4) SCHEME: `color-scheme` switch and the `dark:` custom variant.
  - `color-variants.ts`: `COLOR_VARIANTS`, a set of Tailwind class strings per color (`text`, `bg*`, `onBg`, `shadow` (hard Figma shadow), `border`, `icon`, plus hover/group-hover forms)
  - `semantic-colors.ts`: `SEMANTIC_COLORS`, which maps meanings (brand, status, level, category, rank, surface, ...) to variants. Group names match the SEMANTIC section of `colors.css`.
  - `icon-map.ts`: `UI_ICONS` (lucide), `BRAND_ICONS` (custom SVG, since lucide v1 has no brand icons), and `ILLUSTRATIONS` / `IllustrationId` (the one map of the 14 SVGs in `public/img/illustrations/`, plus the footer shelf list). `[Figma]` marks icons seen in the design; `[+]` marks icons added because they will likely be needed.
  - `category-style.ts`: `CATEGORY_STYLE`, the one map from a facility category to Tailwind classes (`chip`, `ink`, `panel`, `panelDimmed`, `dot`, `filterActive`).

## Firebase
- `app/lib/firebase.ts` (app + emulator switch only), `firebase-auth.ts` (Auth), `firestore.ts` (Firestore): split so a page downloads only what it uses. `auth.ts` is imported by the navbar on every page, so it has no static Firebase import (it loads `firebase/auth` after hydration); never import `firestore.ts` from a module the navbar or footer imports. `app/lib/auth.ts` (Firebase Auth; role from the email domain: `@mail.ugm.ac.id` student, `@ugm.ac.id` staff), `app/components/layout/auth-gate.tsx` (`RequireAuth` on /my-requests and every booking step after the detail page; `SignedInOnly`).
- `facilities/{id}`: data fields of a facility + `order`. `app/lib/facility-store.ts` subscribes live (`useFacilities`, `useLiveFacility`, `currentFacility`); `FACILITIES` is the seed and the first render. Only ids present in `FACILITIES` show, because their text lives in i18n. Public read, no client writes.
- `requests/{code}`: written by the request form (`app/lib/requests.ts`: `submitRequest`, `useMyRequests`, `useRequest`, `cancelRequest`). Initial status from the level (`INITIAL_STATUS`: direct → readyPickup "Siap diambil"; verification and letter → verifying "Menunggu verifikasi"). Rules: owner only; create checks the level against the facility document; the only later change is the owner cancelling an open request. Staff status changes are not built yet.
- Permission levels (project document "Level"): `LEVEL_REQUIREMENTS` in `app/data/facilities.ts` lists what each level asks for (short form / form + purpose, show or leave the KTM, signed letter, who approves). The request form fields, the catalog card line, the detail checklist (`components/catalog/level-requirements.tsx`), the Summary steps, and `firestore.rules` (purpose, `studentIdDeposit`, `letterFileName` per level) all follow it. KTM = a checkbox ("titip KTM di tempat pengelola"), not an upload.
- `users/{uid}`: student profile from the register page; prefills the request form.
- Rules changes: test against the emulator first, then deploy. The letter PDF is not uploaded (only its file name is saved).

## Conventions
- Code is in English: file names, identifiers, types, and comments. User-facing text (labels, headings, messages) stays Indonesian; keep it in the `app/i18n/` dictionaries keyed by English keys (`room`, `logistics`, `verification`, `letter`, `direct`, `borrowed`).
- Exceptions that stay Indonesian because they are external contracts: URL query params, facility slugs and subcategory keys (used in URLs and illustration file names), and the `{{tags}}` inside the .docx template.
- In components, choose colors by meaning (`SEMANTIC_COLORS.status.available`) instead of using raw palette classes. Add new colors to all three files: palette tokens, the variant, then the semantic mapping.
- Tailwind class strings must stay complete literals so Tailwind can detect them; never build class names dynamically.

## Language (Indonesian / English)
- Indonesian is the default and what the server renders. English is a per-browser preference: the "Bahasa · Language" row (ID / EN) in `layout/settings-menu.tsx` saves `pinjamtedi:lang` in localStorage. URLs do not change. `<LanguageScript />` in the root layout's `<head>` sets `lang` / `data-lang` before paint and, for English, holds the page hidden (`data-lang-pending`, `globals.css`) until `<LanguageReady />` lifts it after hydration (~0.2 s; 1.5 s failsafe), so Indonesian text never flashes.
- Text lives in dictionaries in `app/i18n/`: `locale.ts` (types), `common.ts` (shared labels: categories, permission levels, "Semua"), `facilities.ts` (facility names / descriptions, statuses, locations, specs; `localizeFacility()`), `home.ts` (home sections), `site-layout.ts` (navbar, settings, notifications, shortcut dialog, footer, page names), plus one file per page (`catalog.ts`, `booking-flow.ts`, `my-requests.ts`, `room-schedule.ts`, `how-to-borrow.ts`, ...). Never name a file `layout.ts` / `page.tsx` inside `app/`: Next treats it as a route file.
- Write `const id = { ... }` first, then `const en: typeof id = { ... }` so a missing English string is a type error. Keys are English; dynamic text can be a function (`bellLabel: (n) => ...`).
- In components read text with `useText(DICTIONARY)` or `useLocale()` (from `layout/language.tsx`); this makes the component a client component. Data arrays hold keys (`room: "discussionA"`), not display text.
- Every page is translated. Page `metadata` (title / description), the permission letter (.docx), and text drawn inside SVG illustrations stay Indonesian.

## Facilities
- Source of truth: Google Doc "Doc persiapan ORBIT REPOSITORY" (sections "Peminjaman" and "Level"). `FACILITIES` in `app/data/facilities.ts` holds NO display text: `{ id (slug), category, level, illustration, units, multiUnit?, group?, capacity?, location?, subcategory?, borrowedUntil? }`.
- Adding a facility: one entry in `FACILITIES` + its `{ name, description }` under `copy` in BOTH languages of `app/i18n/facilities.ts`. Catalog, filters, counts, cards, detail, and the request flow pick it up; no component edits. A new category: add it to `CATEGORY_ORDER`, `COMMON_TEXT.categories`, three tokens in `colors.css`, and `CATEGORY_STYLE`.
- Rooms with several units (computer-lab, classroom, discussion-room) are one entry per room built by `rooms()`, sharing `group`; their name is `roomGroups[group].name` + the number ("Lab Komputer 2").
- Components render `localizeFacility(f, locale)` (a `FacilityView`: name, description, location label, status, unit, maxQuantity, availability, meta, specs). Room counts, capacities, locations, durations, and `borrowedUntil` are [dummy] data.
- Illustrations: `<FacilityIllustration id={...} />` (`components/ui/facility-illustration.tsx`), always on a `CATEGORY_STYLE[c].panel` fill (navy SVG lines are unreadable on dark surfaces). Facilities use the Figma "1.4 Katalog" set (`catalog/*` ids, `public/img/illustrations/catalog/`, frame size in `CATALOG_ILLUSTRATION_FRAMES`) where one exists; the original set stays for the home cards, footer shelf, and the few facilities without a catalog drawing. `surat-bertanda-tangan` is not a facility: it marks the "letter" level (`<LetterMark />`). `perangkat-jaringan` is unused, kept for network devices.
- Catalog page (`components/catalog/facility-catalog.tsx`, Figma "1.4 Katalog" node 148:1201): search + Lokasi / Kapasitas / Tanggal menus (`filter-menu.tsx`), category tabs, one section per category (first 4 entries of `FACILITIES` as the preview, "Lihat semua n"), multi-unit rooms collapsed into one card that opens `?grup=`. URL params: `q`, `kategori`, `grup`, `lokasi`, `kapasitas`, `tanggal`. Order inside a category in `FACILITIES` = display order.
- Booking modes (Figma 2.x "per hari" / 3.x "per sesi"): `bookingMode(f)` = `f.bookingMode ?? CATEGORY_BOOKING_MODE[category]` (room → "session", the rest → "daily"). "daily" uses `maxDays` (default 3) and `units`; "session" uses `capacity` and `maxHours` (custom start → end hour inside 08.00–17.00; default 4, classroom / lab / multimedia 8, auditorium / field 9). The selection is the union `DailySelection | SessionSelection` (`app/lib/booking.ts`: `validateSelection`, `toSelectionQuery` / `parseSelectionQuery`; URL daily `?ambil=&kembali=&jumlah=`, session `?hari=&mulai=&selesai=&jumlah=`, e.g. `mulai=8&selesai=10` = 08.00–10.00). Everything mode-specific (Scheduler, summary rows, "Pengajuan saya" line, letter period, schedule-cell link) lives in `BOOKING_MODES` (`components/catalog/booking/registry.tsx`); never branch on category. Availability is separate: `app/data/availability.ts` (`getDailyAvailability`, `getHourAvailability`, [dummy]); the schedulers, "Cek ketersediaan" (`room-schedule`), and the home "Ruang kosong hari ini" all read it, so they always agree.
- Booking flow UI (Figma revisions): calendars show ONE week (Mon–Sun, ‹ ›) and color the cell BACKGROUND by state (green many/in stock, orange few, gray + red text full/sold out, gray closed; selected = yellow, loan days = light yellow), no dots. Rooms pick in two steps on `/schedule`: day, then hours (`?hari=` via `window.history.pushState`, so Back returns to the days). Right column: quantity card (units / participants) above the summary. The form shows "Ketentuan peminjaman" (`BOOKING_TEXT.request.rules[mode]`) before the agreement; the summary has no QR / pickup code, only the "Saat ambil / Saat datang" box linking to `/how-to-borrow#ketentuan`. Level names everywhere: Langsung / Verifikasi / Butuh surat; request statuses: Siap diambil / Menunggu verifikasi.
- Category colors (`category-*` solid, `category-*-soft` / `-ink` pairs) only mark the category; status and permission level keep `status-*` / `level-*`. Use `<CategoryBadge />` or `CATEGORY_STYLE`, never raw classes.

## Dark mode and color tokens
- Light is the default. Dark mode is opt-in through the "Mode gelap" switch in `layout/settings-menu.tsx`, which sets `data-theme="dark"` on `<html>` and saves `pinjamtedi:theme` in localStorage (`layout/theme.tsx`, `useTheme()`). `<ThemeScript />` in the root layout's `<head>` applies the saved choice before the first paint; keep `suppressHydrationWarning` on `<html>`. The OS setting is not used.
- **No raw hex in components.** Use theme tokens, which switch automatically: `bg-page` (sky page), `bg-surface` (white cards), `bg-surface-warm` (cream), `bg-surface-row` (yellow rows), `bg-surface-inverse` (navy blocks), `text-ink` (headings, navy), `text-ink-body`, `text-ink-muted`, `text-link`, `border-line-strong` (the 2px Figma outline), `border-line`, `bg-pair-*-bg` / `text-pair-*-fg` or the semantic `status-*` / `level-*` pairs. Never use `dark:` to swap colors.
- **Decide the role of navy before using it.** Navy as ink (text, outline, shadow on a surface) → `text-ink` / `border-line-strong` / `var(--color-shadow)`; these turn light in dark mode. Navy text ON yellow / orange / mint / periwinkle → `text-on-accent` / `text-on-primary` / `text-on-secondary`; these stay navy. Headings get `text-ink` from the base layer, so a heading on an accent fill needs an explicit `text-on-*`. Muted text on those fills → `text-on-accent-muted`.
- Hard shadows: keep the Figma offsets and use the shadow tokens, e.g. `shadow-[5px_5px_0_0_var(--color-shadow)]`, `var(--color-shadow-accent)` (purple), `var(--color-shadow-interactive)` (blue), or `shadow-hard-*`.
- Accent fills (`bg-brand-primary`, `bg-brand-secondary`, `bg-sun-200`, `bg-mint-300`, `bg-periwinkle-400`, `bg-tangerine-400`, `bg-status-available`) are the same in both themes; the orange CTA stays orange.
- **Adding a color:** add one line to the THEME section of `colors.css` with both values (`--color-x: light-dark(<light>, <dark>)`), check WCAG AA in both themes (4.5:1 text, 3:1 large text and UI parts), then use `bg-x` / `text-x`. Colors that never change go in PALETTE. Add a variant / semantic mapping only when the color has a meaning.
- `dark:` (custom variant) is only for layout differences that exist in one theme, e.g. the lit panel behind the hero illustration. It does not apply in print.
- Lightning CSS compiles `light-dark()` to a polyfill switched on `:root`, so tokens cannot be forced light inside a subtree. Always-light areas use fixed palette classes: the letter paper in `letter-preview.tsx` (`bg-white` + `text-black`) and the QR code in `request-summary.tsx`. `@media print` forces the light theme.
- Deliberate deviations from Figma, for WCAG AA: `ink-muted-on-page` = `#4f6379` for muted text on the sky page (Figma `#5b6f87` is 4.30:1 there); `on-accent-muted` = `#45566b` for muted text on yellow / mint fills (Figma `#5b6f87` is 3.6:1 / 3.2:1). Use `text-ink-muted-on-page` for muted text that sits directly on `bg-page`.
- Illustrations (`public/img`) use navy lines and white fills; they stay readable on the fixed accent panels (yellow / mint / periwinkle). Do not edit the SVG files for dark mode.
